## 実装メモ

`docs/attribute-contract.md` は、supported attributes の一覧だけではなく、どの属性が request-capable な状態を作るのかを明記した。ここで request-capable とは、実際に network request を実行できる設定を持つ状態という意味で、`mx-trigger` だけを持つ要素は request を発火しない。

request attribute は precedence を持たないことにした。つまり `mx-get` と `mx-post` が同じ要素にある場合にどちらかを選ぶのではなく、`MHX_VALIDATE_CONFLICTING_REQUEST_METHODS` で拒否する。これは現在の `first_validation_error` の実装と合わせている。

`mx-target` は trigger-local `target:`、element-level `mx-target`、triggering element の順で解決される。bare な `closest` / `find` / `next` / `previous` は selector として未完成なので、`MHX_PARSE_INVALID_SELECTOR` として扱うことを明文化した。

`mx-vals` は flat JSON scalar だけを許可する。flat JSON scalar とは、値が string / number / boolean / null のどれかで、object や array を含まない JSON object のこと。form body との merge では form fields の後ろに `mx-vals` を追加するため、同じ key を map として解釈する利用者には後勝ちとして見える。

## 実装メモ: request lifecycle and queue

`RequestManager` は element id ごとに current task と pending task の配列を持っている。今回の重要点は `complete(element_id, task_id)` の `task_id` を実際に使うことだった。これまでは element id だけが一致すれば current を消して次の pending に進めていたため、`replace` で新しい request を current にした後、古い request の abort / network failure callback が遅れて来ると、新しい current を消せる余地があった。

この stale callback は、もう古くなった非同期 callback という意味で使っている。非同期処理では、開始順と完了順が一致しない。だから queue の cleanup は「element が同じ」だけでなく「current task id が同じ」ことを条件にする必要がある。

`replace` は active request を cancel し、pending request も cancel 済みにしてから捨てるようにした。`queue:last` も pending を置き換える mode なので、置き換えられる pending task を cancel 済みにしてから外す。pending task はまだ JS fetch callback id を持たないことが多いが、local cancellation flag を立てることで低レベル contract と実装の意味を揃えた。

test は `src/network/manager_test.mbt` に寄せた。ここは DOM や browser fetch に依存しない pure な scheduling layer なので、今回の issue の scope に合っている。`drop` は repeated trigger を無視すること、`queue:all` は FIFO で進むこと、replace 後の stale completion が current request を消さないことを確認した。

## 実装メモ: swap engine contract

`src/swap/swap.mbt` はすでに `SwapOptions.strategy` を DOM primitive に直結していたため、runtime code の変更は不要だった。今回の中心は「何を stable contract と呼ぶか」を文書と smoke test に落とすことだった。

`delete` と `none` は response body を使わない。特に `none` は「request hooks だけ」と書くと現在の実装より狭い説明になる。現在の runtime は成功 response 後に target を解決し、`mhx:beforeSwap` と `mhx:afterSwap` を dispatch した上で no-op strategy を実行する。つまり DOM は変わらないが、swap lifecycle は観測できる。

missing target は target 解決の段階で止まるため、swap 前後の lifecycle は出ない。かわりに structured selector error として `mhx:error` が出る。この structured error は、低レベル DOM primitive の失敗ではなく「swap 先が DOM element として解決できなかった」という contract にした。

npm smoke は browser DOM 全体を持ち込まず、`src/ffi/mhx_ffi.js` の低レベル関数を fixture element に当てる形にした。これは mhx の swap engine が実際に呼ぶ境界を確認するためで、virtual DOM や template engine の仮定を入れない。

## 実装メモ: structured error model

既存の `src/core/error.mbt` はすでに `MhxError::category()`、`code()`、`message()`、`attribute()`、`position()`、`source_element()`、`ToJson` を持っていた。今回は public surface を広げるというより、既存 surface を「stable contract」として文書化し、欠けていた event detail の情報量を揃える作業になった。

nullable semantics は JavaScript 側の event detail では `null` として扱う。docs には利用者が見る public payload の意味を中心に書き、MoonBit 側の helper は `attribute()` / `source_element()` / `position()` が `Option` を返すことを API として残した。

request failure の `mhx:afterRequest` は以前 `error: { category, message }` だけを渡していた。これだと handler は structured error を受け取れても、event listener は stable `code` や `recoverable` を読めない。`element_dispatch_request_event` の error 引数を full JSON string に変え、失敗時は `error.to_json().stringify()` を渡すようにした。

abort error は source element なしの helper だけだったため、runtime callback path 用に `abort_error_for_element` を追加した。abort は application failure ではなく runtime coordination だが、logging では「どの element の request が abort されたか」が診断に必要になる。
